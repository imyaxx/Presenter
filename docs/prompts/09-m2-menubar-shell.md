## Objective
Turn the app from a skeleton into a working menu-bar product: at launch it builds the real object graph, recovers an interrupted session before anything else, and shows a menu-bar icon whose shape tells the session state and a popover where the user sees the state, picks a profile from `profiles.json` to activate it, stops it, retries a failed restore, and quits. After this branch a person can write a profile file by hand and run the whole activate and deactivate flow with real system effects (the M2 acceptance sentence, minus the HUD and the hotkey, which are the next branches). This is the first branch in which the shipped app itself changes the user's real system, so Part B runs under the adapter check backup and diff discipline.

## Two parts, and the rule between them
- Part A (build): everything in Scope except the manual run. Safe: no automated test changes a real setting (docs/06, ADR-040). Do all of Part A first, commit it, make `make verify` pass.
- Part B (verify): the staged run with the user on the real Mac, below. Interactive by design: asking the user to look at the screen and report is required and is not a "blocking question". Part B starts only after one AskUserQuestion confirming the user is at the Mac, has saved open work, and agrees to the visible effects (desktop icons, Dock and menu bar hide, the wallpaper changes, the apps you will name are hidden, Automation prompts). If the user is absent or says no, stop after Part A, open the PR with Part B marked "not run", and say so. Never run Part B unattended.

## Decisions already made (record them in the docs; do not re-decide)
1. Composition. `App/Sources/Application/AppEnvironment.swift` builds the graph once at launch from `PlatformComposition`: `ProfileStore` and `SessionStore` over `FileManagerFileStore` in the support directory, `StandardActionFactory(ports:wallpaperLocations:)`, `SessionController` with `SystemSessionClock` and `OSSessionLogger`. It is the only place that instantiates the concrete types. If building fails (`PlatformCompositionError`), the app still starts, shows the failure in the popover with one localized message and a Quit item, and never activates anything.
2. Recovery first. `recoverIfNeeded()` is started from the app's launch path, not from a view's `.task` or `onAppear` (whether a `MenuBarExtra` window builds its content before the first click is not known; do not depend on it). Until it finishes the popover shows a "Restoring" state and offers no trigger. The controller already refuses activation before recovery (`recoveryNotRun`); the UI must not rely on that refusal.
3. Protocols for the UI. `Features/MenuBar` must not import `Platform` and must be testable without the real controller (the ModeKit test fakes are not available to the app tests): define small role-named protocols in `Features/MenuBar` for what the view model needs (a session-controlling protocol with the state stream and the five triggers, a profile-loading protocol, a profiles-folder-revealing protocol); `SessionController` and `ProfileStore` conform through extensions in `Application/`; the revealer has a Platform implementation (decision 9). App tests use hand-written fakes under `App/Tests/Features/MenuBar/Support`.
4. View model. `MenuBarViewModel`: `@Observable`, `@MainActor`, no system calls, no string literals for UI text (only `L10n`). It follows the controller's `stateUpdates()` stream (one loop, owned by the environment, cancelled on termination, no fire-and-forget `Task`), holds the profile list, a presentation state derived from `SessionState` (restoring at launch, idle, applying, active, restoring, rolling back, degraded with its reason, build failure), the last notice, and the intents: `popoverDidOpen()` (reload profiles), `activate(_:)`, `deactivate()`, `retryRestore()`, `requestDiscardUnreadableSession()` / `confirmDiscard()` / `cancelDiscard()` (inline two-step confirmation, no modal dialog), `revealProfilesFolder()`. Triggers the state does not accept are disabled in the UI and the view model also ignores them; a `TriggerResult.ignored` is never an error message.
5. Popover content (docs/04: width about 320 pt; system controls and semantic system colors and fonts only; no custom colors, no tokens, no custom materials: the design system is the later branch `feat/design-system-foundation`, which restyles this popover without changing behavior). Top: the state line (Inactive, Applying, Active: profile name with a live elapsed time via a SwiftUI timer text with monospaced digits, Restoring, Needs attention). Middle: the profile list as buttons (click activates); empty state when there are none ("No profiles yet" plus one line saying profiles are created in Settings, which arrives in a later version, and the item that reveals the profiles folder); when active, the list is replaced by the active profile with a Stop button. Notices appear under the state line and can be dismissed. Bottom: "Show Profiles in Finder", Quit, and the version as a secondary caption. No Settings item yet. Every control is keyboard reachable and VoiceOver-labelled; icon-only controls have accessibility labels. Strings: a new `L10n+Menu` entries (English and Russian, translator comments, keys namespaced `menu.*`), plus `L10n` entries for action names and notices.
6. Menu-bar icon. Three states with different SHAPES (not color): idle, active, needs attention. Interim: SF Symbols `display`, `eye.slash`, `exclamationmark.triangle`, template rendering, with an accessibility label per state; applying, restoring and rolling back keep the previous shape. Record in the docs that `feat/design-system-foundation` replaces them with the vector assets of docs/04; do not build custom assets here.
7. Notices and failures, mapped by action identifier and phase only (never by parsing `reason`): a failed activation (which action, rolled back, or rollback also failed); after a deactivation, the actions left unchanged because the user changed them (named); after a launch recovery that restored something ("Restored your settings after an interrupted session", with the same skipped list); a degraded restore (the failed actions named, Retry restore); an unreadable `session.json` (Discard with the inline confirmation; the file is never touched otherwise); a profiles file that cannot be read, is corrupted or newer than the app (message by `StoreError` case, the file is never overwritten here). For a failed Dock action the notice also says Presenter needs permission to control System Events and names the place (System Settings, Privacy & Security, Automation); a deep link belongs to the Permissions branch of M3.
8. Quit while a session is active restores first. `applicationShouldTerminate` returns `.terminateLater`, a `QuitCoordinator` (testable, injected controller and clock) deactivates, waits at most 15 s (named constant; the macOS behavior for logout and shutdown is `UNVERIFIED`), then replies; a restore that is still running at the deadline, or a degraded result, still allows the quit because `session.json` persists and the next launch recovers (ADR-008). Quit from the popover and Cmd+Q use the same path.
9. Profiles folder. A Platform adapter named by mechanism (for example `NSWorkspaceProfilesFolderRevealer` under `Platform/Workspace`) creates the support directory when it is missing and reveals it in Finder. The reveal call itself is never run by an automated test; the directory creation is unit-tested with an injected base.
10. Single instance. A second launch of the same bundle identifier must not run: it activates the first instance and exits before building anything (two instances would race on `session.json`). Implemented in the normal launch path only, after `AdapterCheckLauncher.runIfRequested` (check mode uses `open -n` and its own support directory; it must keep working). A small Platform type plus a pure decision function that is unit-tested.
11. ADR-043 "Menu bar shell": the points above (recovery at launch, protocols at the Features boundary, quit restores, single instance, interim icons), each with context, decision, consequence, "proposed by the assistant; user to confirm".

## Requirements
- Architecture: `git grep -n "Platform" App/Sources/Features` prints nothing; `Features` imports only ModeKit and SwiftUI (the view model may import Foundation and Observation); `Application/` is the only place that instantiates concrete platform types; `Features/` never refers to `DeveloperTools/`; ModeKit imports Foundation only.
- Code: docs/03-code-standards.md. No TODOs, no stubs, no commented-out code, no unrequested abstractions, no `Utils`/`Helpers`/`Manager`/`Common` names, no boolean parameters, no force unwraps, no `try?` that discards a failure without a justifying comment, no `print`, no singletons, no `DispatchQueue`. A view body at most 60 lines (split into subviews); files at most 300 lines; functions at most 50. View models hold no system calls.
- Concurrency: Swift 6 strict, zero warnings.
- Edge cases to handle and test (view model and coordinator with fakes): state stream mapping for every `SessionState` and `DegradedReason`; triggers disabled per state; double click on a profile; activation failure at each phase (the action named, the rolled-back flag); deactivation with skipped actions; recovery outcomes `restored`, `partiallyRestored`, `blocked`, `nothingToRecover`; profiles load failures per `StoreError` case; profiles reloaded on each `popoverDidOpen()`; the discard two-step flow including cancel; quit while idle, while active, while a restore exceeds the deadline (fake clock), and while degraded; building failure state; single instance decision (no other instance, one other, the current process excluded); the folder creation.
- UI: Light, Dark and System; English and Russian; no truncation at Russian string lengths (the popover width is fixed, text wraps); Reduce Motion honored (no custom animation).
